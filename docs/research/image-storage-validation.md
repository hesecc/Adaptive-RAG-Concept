# 图片资料库与存储适配验收记录

验收日期：2026-11-16。本记录针对当前工作区实现；未切换生产存储，未调用付费模型，未执行 Git 提交或推送。

## 已实现与实际覆盖

- 新增 `/images` 图片资料库和 `/assets` 接口，支持管理员上传、说明编辑、删除、索引重试，以及普通账号浏览、描述检索、原图与缩略图读取、历史 trace 回放。
- 图片检索使用标题、人工说明、标签和已有 OCR 文本。无模型模式执行文字检索，明确显示 `lexical` 与零模型调用；语义路径复用文本 Embedding，没有新增共享图文向量模型。
- PostgreSQL 可保存文档知识、trace、图片元数据与索引任务；S3 兼容接口保存字节；Milvus 保存图片文字的派生向量。账号仍使用 SQLite，文档 dense 实现没有自动迁往 Milvus。
- 元数据与任务同事务写入。查询、图片读回和历史 trace 回放核验当前版本及访问权限；删除先撤销访问，再异步清理向量。

| 配置与静态检查 | Compose 配置展开、`uv lock --check`、JS 语法、`git diff --check` 通过 |

独立页面 QA 初轮发现断线时仅显示 `Failed to fetch`。公共图片 API 请求函数已补充中文连接失败与重试指引，随后由新代理实际浏览器复验通过：断线时显示“无法连接服务，请检查网络或服务状态后重试。”且按钮恢复；同一服务重启后，在原页面重试返回 200，展示新 Trace、真实耗时与零模型调用。“查看全部图片”和历史 Trace 回放也通过，初轮唯一失败项已关闭。复验服务与标签页均已关闭。

整套回归曾触发旧 `test_timeout_has_a_terminal_trace` 的时序波动。原测试将插件超时和真实 Trace 写盘共同限制为 50ms；模拟 150ms 写入延迟时，查询返回早于后台写盘结束，随后读不到 Trace，清理又遇到文件占用。相同复现在改动前的 HEAD 也失败。本次仅将该测试预算调为 1 秒，保留超时与终止 Trace 断言，未改变运行时超时策略。相关 21 项可观察性测试通过，最终全套通过；这不表示任意极短超时配置下都保证 Trace 落盘。
